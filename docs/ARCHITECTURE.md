# How OverBoard works

Notes for contributors: how each part is built and why. What's planned next is in [ROADMAP.md](ROADMAP.md).

## The HTML overlay (v1)

`overlay/ink_overlay.html` is a self-contained block pasted before `</body>`. Key facts for contributors:

- **Coordinates.** Ink is stored in CSS px relative to the *page column*: a band `CW` wide (widest `.page` + 96 px margin), centered in the body. The canvas spans the full window; `OX` is where the column starts inside it. This keeps ink aligned across zoom and resize.
- **Stroke format.** `{ c: color, w: width, e: 1 if eraser, h: 1 if highlight, p: [x0,y0,x1,y1,...] }`. Data is `{ v: 2, t: savedAtMs, active: "P1", periods: { P1: [strokes], ... } }`.
- **Colors.** Pen and highlighter each remember their own color (`penColor`, `hlColor`; highlighter starts yellow `#fdd835`, saved as `ink-hl-color`). Toggling the highlighter swaps between them.
- **Layers.** Pen ink on `#ink-canvas`; highlights on `#ink-hl` underneath with `mix-blend-mode: multiply`; eraser strokes cut through both.
- **Rendering.** Strokes are quadratic curves through sample midpoints, with an exponential smoothing filter on input (`SMOOTHING` level 0–8). Live drawing renders the identical curve piece by piece.
- **Input (SMART Board on macOS, observed with `tools/board-probe.html`).** Pen tip → `pointerType: "pen"`, `buttons: 1`. Palm/fist/side of hand → `"pen"` with `buttons: 32` (eraser). Finger and the pen's round end → `"mouse"`. Contact size is always 1×1. Only one pointer reaches the browser at a time. A still finger is held back by the driver until it moves.
- **Saving.** Browser IndexedDB (database `ink-data`, store `ink`, key `ink-v2:<path>:<title>`; v21+), plus optional File System Access write into the `<script id="ink-data">` block of the .html file.
- **Print.** `beforeprint` redraws each page's strokes as vectors at `PRINT_SCALE` onto per-page canvases.

## The PDF app (v2)

`app/index.html` opens a PDF in the browser (no server, no build step; plain ES modules). The original v2 plan, all done:

1. ✅ **App shell** at `app/` (linked from the demo page): drop zone, file picker, drop anywhere, "Open again" list.
2. ✅ **Render with PDF.js** `4.10.38` (pinned in `app/libs.js`, served from `app/vendor/`; refresh with `tools/vendor_libs.py`). Each page is a `.pg` element sized to the page.
3. ✅ **One ink canvas per page** (plus a highlighter canvas under it, only when the page has highlights). Kept the side space: each page has a 36 pt writable gutter left and right; it doesn't export.
4. ✅ **Lazy rendering.** Page images render within 1 screen of the viewport and are freed 2 screens away; ink canvases exist only for nearby pages that have ink. Page sizes start at page 1's size and are corrected in the background.
5. ✅ **Shared code.** `shared/ink-core.js` (curve drawing, live drawing, smoothing, pen/palm/finger classification, hold-to-repeat, confirm tap) and `shared/toolbar.css` are imported by the app and inlined into the overlay by `tools/build.py` (overlay v16). The Highlighter ▾ menu (`makeHlMenu`, `seeThrough`, `hlInk`, `placeMenu`) and its styles are shared too, so the app and the overlay behave the same. The overlay is still one self-contained paste-in block.
6. ✅ **Persistence** in IndexedDB (`overboard` database: `ink` and `files` stores) keyed by the SHA-256 of the PDF bytes. **Save ink / Load ink** uses an `.overboard.json` sidecar.
7. ✅ **Export PDF** with pdf-lib `1.17.1`: strokes become vector Bézier paths in the original PDF; highlights use the Multiply blend mode under the pen ink.
8. ✅ **Page navigation:** page number box, ▲/▼ Page, and the PDF outline as a Chapters panel (current chapter marked).

Key facts for contributors:

- **Coordinates.** Ink is in PDF points measured from the top-left of the page *as shown* (PDF.js viewport at scale 1, so `/Rotate` and the crop box are already applied). Screen px = points × `zoom` (+ the gutter). Zoom never moves ink.
- **Stroke format.** v1's stroke plus `page` (1-based): `{ page, c, w, e, h, o, p }`, with `w` and `p` in points. `o: 1` (with `h: 1`) is a **cover**: an opaque highlighter stroke (see below). Data without `o` loads as before. Data is `{ v: 3, t, active, at: lastPage, periods: { P1: [strokes in drawing order] } }`. The sidecar wraps the same periods: `{ app: "OverBoard", kind: "pdf-ink", v: 3, pdf: { sha256, name, pages }, t, active, periods }`.
- **Sizes.** Toolbar sizes keep v1's units (1/96 in), stored as points (× 0.75), so pen and highlighter scale with the page. Eraser and palm widths are screen px ÷ zoom, so the palm feels the same at any zoom.
- **Colors.** Same as v1: `penColor` / `hlColor`, highlighter starts yellow, saved as `ink-hl-color` (shared with the overlay on the same site). Highlight strength (▾ slider, 10–100%, default 50 = v1's look, saved as `ink-hl-strength`) sets how far the color is mixed toward white when the stroke is drawn; the mixed color is stored in `c`, so stored ink and export don't change. Because highlights multiply, this works like opacity and text stays black.
- **Clear** clears only the current page in the PDF app (Undo restores it).
- **Clear page / Clear all** (both apps). Overlay, and a PDF without chapters: two buttons in one row, Clear page (one tap) and Clear all ("Sure?"); with fewer than two pages only Clear all shows, labeled Clear, full width. A PDF with chapters: Chapters | Clear ▸, where Clear ▸ opens `#ob-clearmenu` (This page / All pages with "Sure?"), and `layoutClear()` puts Clear on the side the menu opens (right of Chapters, left of it when the toolbar is on the right). Menus are popouts from `makePopMenu()` in `shared/ink-core.js` (open on tap; close on a choice, a tap elsewhere or Escape; one at a time). Only the active period is cleared. PDF app: `Ink.clearAll()`, and `lastCleared` holds `{ page, before }` or `{ all }` so Undo restores the exact old order. Overlay: `lastCleared` is the whole stroke list before the clear; a stroke belongs to the `.page` its vertical middle falls on (the gap below a page and its side margins count as that page), and "this page" is the page at the middle of the screen.
- **Toolbar fits short screens** (both apps). `fitTools()` measures the toolbar at full size and, if it is taller than 96% of the window, zooms it and its popouts down to fit (checked twice, since text doesn't scale exactly), instead of letting it scroll. `placeMenu()` divides by a popout's zoom. Called on open, resize, Move/Hide/Show and (overlay) every page zoom. The zoom % has 40 px side buttons and no ellipsis, so "100%" fits with the Mac's system font.
- **Overlay zoom** (v18). CSS `zoom` on `<html>`, undone (`zoom: 1/Z`) on `#ink-bar`, `#ink-show` and the popouts. Ink stays in the worksheet's own CSS px: `pt()` divides screen px by `Z`, `size()` uses `clientWidth / Z` and a canvas scale of `devicePixelRatio × Z`, and palm/eraser widths are ÷ Z (same size on screen, like the app). Fit = widest `.page` fills the window minus the toolbar on both sides (no `.page`: 100%). Zoom keeps the middle of the screen in place; Ctrl+wheel is taken over; `beforeprint` prints at 100% and `afterprint` puts the zoom back. Not remembered between visits (the PDF app starts at Fit each time too).
- **Undo / Redo** (both apps). `#ink-undo` splits Undo's cell into ↶ and ↷ (no new row; the toolbar has ~10 px to spare at 1080p). Undo pushes what it took onto a redo list (a stroke, or `{ cleared }` after undoing a Clear); Redo pops it (re-adding the stroke, or clearing again). New ink, Clear, a period switch and loading ink empty the list; ↷ is disabled when it's empty. Keys come from `historyKey()` in `shared/ink-core.js`: Ctrl/⌘+Z undo; Ctrl/⌘+Y, Ctrl/⌘+R, Ctrl/⌘+Shift+Z redo; F5 and Ctrl/⌘+Shift+R are swallowed (`preventDefault`), so only the browser's button reloads. In a text box (page number, Find, worksheet fill-ins) undo/redo keys are left to the box.
- **Reload safety** (PDF app). The IndexedDB autosave waits 3 s, and a write started in `pagehide` can be cut off by the unload. So `pagehide` also writes the ink to `localStorage` (`ob-unsaved:<hash>`, synchronous); opening the PDF uses it when its `t` is newer than the IndexedDB copy, saves it, and removes it. `sessionStorage` `ob-open` holds the open PDF's hash (cleared first thing on close), so a reload reopens it from the **Open again** store. The overlay (v21+) does the same: on `pagehide` / tab hidden it also writes `localStorage` under its `ink-v2:` key, and removes it once IndexedDB has that ink. Ink that v20 and older left in `localStorage` moves to IndexedDB the first time the worksheet opens. Drawing waits until the IndexedDB copy has been read (a few ms).
- **Export.** Each page's ink is mapped back with the inverse of the PDF.js viewport transform. PDFs have no eraser, so erasers are applied geometrically on export: sample points of earlier strokes under the eraser path are dropped and the strokes split there. Only the active period is exported.
- **Memory** (measured headless at 1920×1080, devicePixelRatio 2, 320-page book): page process peaks around 640 MB while fast-scrolling, about 450 MB above the empty app, and settles near 520 MB. Each page image is capped at 12 MP.

Added after v2:

- **Save windows start next to the original** (Chrome/Edge). A dropped file (`getAsFileSystemHandle`, asked for during the drop), a tap on the drop box (`showOpenFilePicker`, id `overboard-open`; other browsers use the plain `<input type=file>`) and a Finder launch (`launchQueue`) all give a file handle. `saveBoardCopy()` and Save ink into PDF pass it as `startIn` and leave out their picker `id`, since a remembered id folder can win over `startIn`; with no handle (Open again, plain input) they use the id. The PDF's handle is kept as `doc.origin`. The overlay can't do this for itself: a page opened from disk has no handle to its own file.
- **HTML in the app.** Dropping an `.html` worksheet makes a `Name_board.html` copy with the overlay, the same as the installer (`app/html.js` mirrors `ink_overlay_installer.py`; output is byte-identical).
- **Blank notebooks** (`app/notebook.js`). The start screen's paper buttons make a one-page US Letter PDF with pdf-lib; the paper (lines, grid, dots or isometric triangles) is drawn as vector operators in the page. The PDF's Keywords hold `overboard-notebook-<16 hex>`, and when the app opens a PDF with that mark it keys the ink by `notebook-<id>` instead of the SHA-256, because adding or removing a page rewrites the file. Each page change loads the base bytes, inserts or removes a page with pdf-lib, reopens the result in the viewer, moves every period's strokes with `shiftInk`, stores the new file under the same key (Open again) and resets Undo. Export PDF drops the mark, so an export is a plain PDF.
- **Save ink into PDF** (opt-in, `app/embed.js`). The ink (sidecar format) is stored as the attachment `overboard-ink.json`, written as one standard incremental update after the original bytes: new embedded-file, filespec, name-tree and Names objects, a new version of the catalog, and an xref section of the same kind as the original's (table or stream) with `/Prev`. The trailer carries `/OverBoardBase <original length>`, so each save writes *original + a fresh update* (the file doesn't grow) and OverBoard hashes only the original bytes (same ink key as the plain PDF). If another app saves after us, the whole file counts as the original. Encrypted PDFs are refused. Export PDF uses the original bytes, so exports don't carry the stored ink. The chosen file handle is remembered in IndexedDB (`links` store); after a browser restart the button asks for permission again.

- **Self-hosted libraries.** PDF.js and pdf-lib are served from `app/vendor/` (copied by `tools/vendor_libs.py`), so the app never contacts another site.
- **Version stamp.** `app/index.html` loads its modules through a small loader that reads `app/version.json` fresh and maps every module to `?v=<hash>` with an import map (the hash covers `app/` and `shared/`; `tools/build.py` writes it). An older cached copy of the page reloads itself once. This avoids mixing files during GitHub Pages' 10-minute browser cache.
- **Offline copy and installing** (`app/sw.js`, `app/offline.js`, `app/manifest.json`). The service worker caches every file in `app/` (vendor/ included) and `shared/`: `tools/build.py` writes `VERSION` and `FILES` (path → first 16 hex of SHA-256) at the top of `sw.js`; the version hashes the file list and sw.js's own code. `sw.js` is left out of `version.json` (it would hash itself). The rule is the same as the version stamp: pages never mix versions.
  - The list also holds `overlay/ink_overlay.html`, which `app/html.js` fetches to make HTML board copies.
  - **Install** downloads every file (`cache: 'no-cache'`) and checks its hash. Any miss or mismatch (e.g. GitHub Pages mid-deploy) throws, the half-filled cache is deleted, and the old version stays; the browser retries on a later visit.
  - **Switch.** No `clients.claim()`: a page keeps the version it loaded with. The new worker waits; it activates when every OverBoard window is closed (the browser does this), or when `index.html`'s loader, before starting the app, posts `ob-switch` to the waiting worker. The worker counts the window clients in its scope (rechecking for up to 1 s, since a page that is closing or being replaced can linger) and calls `skipWaiting()` if the asking page is the only one; the loader reloads on `controllerchange`, or starts the current version on `ob-wait` (or after 8 s). A switch that lands after the app started reloads only on the start screen.
  - **Activate** deletes the other `overboard-*` caches. **Fetch** answers any listed file from this version's cache only, ignoring `?v=` (directory URLs map to `index.html`); everything else goes to the network.
  - **Install app** (start screen, `#ob-install`) shows only after `beforeinstallprompt`, which the inline loader catches early. **Opening PDFs from Finder**: `file_handlers` in the manifest plus `launchQueue` → the normal `openFile`.
  - **Tests** (`tests/offline.spec.js`) serve a private copy of the site per test and "deploy" by running that copy's `build.py`. Playwright attaches a debugger to every service worker, which can hold back a `skipWaiting()` indefinitely, so the switch-at-load test runs in a plain headless Chrome driven by a page on the site. The rest of the suite runs with `serviceWorkers: 'block'`, so `page.route` keeps working there.
- **Toolbar fits 1080p.** Page ▲ / number / ▼ share one row, and Export PDF, ink files, Save ink into PDF, Open another PDF and Move toolbar are in a File ▸ menu beside the toolbar.
- **Tests.** Playwright suite in `tests/` plus both `--check`s, run on every pull request.
- **Text layer and links** (`app/textlayer.js`). Each page gets a PDF.js `TextLayer` (selectable, invisible text over the image) and a `.links` box of `<a>` elements from its Link annotations. Both are made after the page image renders and freed with it, so only pages near the screen have them. They are laid out once at scale 1 in % of the page; `--scale-factor` on each `.pg` (= zoom) sizes the text, so zooming doesn't rebuild them. Rotated pages: `TextLayer` sets `data-main-rotation` and `app.css` rotates the layer (rules adapted from PDF.js's `pdf_viewer.css`); link boxes come from the rotated viewport. External links (`url`, which PDF.js only fills for safe schemes) open in a new tab; internal ones (`dest`, or Next/Prev/First/Last page actions) go through `viewer.goTo`.
  - **Input.** In Write mode the layers have `pointer-events: none`, so pen, palm and finger draw, erase and scroll exactly as before. In Scroll mode a press on text or a link is left to the browser (select, click); a press anywhere else still drag-scrolls, and a tap there clears the selection.
  - **Find text** (`app/find.js`, File menu or Ctrl/⌘+F) reads each page with `getTextContent` (kept as plain strings for the next search), lists up to 500 hits with page numbers, and marks matches inside the live text layers (`<mark class="hit">`). Matches that cross two text runs are listed but not marked.
  - **Exports keep the text.** Export PDF only appends drawing operators to the original pages and Save ink into PDF only appends an update, so the original text, fonts and links are untouched. Tests check `getTextContent` on both outputs equals the original's.

- **Highlighter ▾ Cover.** The Highlighter button is split: the main part toggles the highlighter, the ▾ (same row, so the toolbar doesn't grow) opens `#ob-hlmenu`, a popout like the File menu: Highlight (see-through multiply) with a strength slider, or Cover in black, light gray, white or any color (the toolbar's color picker; dark gray was dropped in v26). Moving the slider switches to Highlight but leaves the menu open. It stays open until a choice, a tap elsewhere, or Escape; lifting the pen or finger never closes it (no long-press: invisible, and the SMART driver holds back a still finger). The chosen mode shows on the button ("Highlighter" / "Cover") and is remembered (`ink-hl-mode`, `ink-cover-color`); palette colors set the cover's own color while covering. Covers are stored as `{ h: 1, o: 1 }` and drawn on the pen canvas in drawing order (above the page and its text layer, not multiplied), so eraser, palm and Undo remove them like any stroke. An older app version would draw them as multiply highlights (black still hides).
  - **Export.** Covers are drawn opaque with the pen ink, over the page. They do **not** remove the text underneath (we never delete or rasterize the PDF's text), so when the exported period still has covers after erasers, a dialog says plainly that covered answers can still be copied from the PDF, and the status line repeats it.
  - **HTML overlay (v16; v17 adds Redo; v18 File ▸ and zoom; v19 Clear page / Clear all and a toolbar that fits short screens)** has the same ▾ menu, covers and strength slider (shared code). Covers go on `#ink-canvas` above the page and print as solid bars. **Save PDF** with covers first asks, via `confirm()`, after saying the text under covers stays in the PDF and in the worksheet file. Ctrl+P skips that question, since printing can't be stopped from `beforeprint`. Older overlays draw covers as multiply highlights.

- **Board not working?** (`app/report/index.html`, v24). One self-contained page, linked from the app's start screen and File ▸ in both apps (the overlay opens the website's copy with `?from=overlay&ov=vN`, read from its own START comment).
  - **Steps:** finger, pen, palm wipe, board eraser, two fingers. One per screen, big text. `Next` always works, with or without input (also Enter / → for boards whose touch doesn't work at all); some steps have a "Skip: I don't have one". Feedback is always positive ("✓ Got it! I saw 2 lines", "✓ Something happened, but not a line"), never "wrong". A button press made with a palm (`pointerKind` = palm), or within 450 ms of a screen change, is ignored, so a wipe can't skip a step.
  - **Recording:** document-level capture listeners for pointer, touch, wheel, contextmenu and Safari gesture events, during the steps only (never on the typing screens). Per step: counts by `pointerType`, by OverBoard's `pointerKind`, by `buttons` (and `eraserButton` for `buttons & 32`), max width/height/pressure, tilt, pointers at once, lines (moved > 30 px) vs taps, events outside the pad, scroll/zoom/right-click/pinch. Up to 150 raw events per step (every pointer change, every 10th move). Device: user agent, `userAgentData` high-entropy values (OS version, model, architecture), screen, DPR, `maxTouchPoints`, pointer/hover media queries, cores, memory, installed or not.
  - **No SMART driver check** here: reaching the driver on `127.0.0.1` from a website triggers Chrome's local-network permission prompt. `tools/board-probe.html` still does it for developers.
  - **Sending:** POST as `text/plain` (no CORS preflight) to `RELAY_URL`, a Google Apps Script web app (`tools/report-relay.gs`, setup in `docs/REPORTS.md`) running as overboard.reporting@gmail.com. It opens an issue labeled `board-report` (summary table plus the JSON, trimmed to fit GitHub's 65,536-character limit) with a fine-grained token kept in Script properties, and emails the full report as an attachment with Reply-To set to the teacher's address. `private` (email, comments) is removed before the issue. Honeypot field `website`; at most 20 reports an hour and 40 a day, 25 thank-you emails a day, and one thank-you per address a week (so a robot can't use up Gmail's ~100 emails a day or pester strangers). With no `RELAY_URL`, or on any failure, the page offers Download / Copy and the email address.
  - **Brand logos:** set `logo: true` in `BRANDS` once `app/report/brands/<id>.svg` exists.

- **Languages and tooltips** (`shared/strings.js`, v24). One table, inlined into the overlay by `tools/build_overlay.py` like `ink-core.js` and imported by the app. Each key is `[en, es, zh, tl, vi, fr, pt, ar]` (order of `obLangs()`); `{name}` placeholders; a missing entry falls back to English.
  - `obLang()`: `localStorage['ob-lang']` (Settings ▸ Language, or the app's start-screen 🌐 list), else the first of `navigator.languages` we have (`fil` → Tagalog), else English. Shared by the app and the overlay on the same site.
  - HTML is marked `data-t` (text), `data-th` (HTML), `data-tt` (title), `data-ta` (aria-label), `data-tp` (placeholder); `obTranslate(root, tr)` fills them and sets `lang` (and `dir="rtl"` for Arabic on the menus, Settings and status line; the toolbar's layout doesn't flip). JS uses `tr('key', vars)`; `setLang()` swaps `tr` and re-translates in place. Shared widgets get the translator as a parameter (`makeSettings` `O.t`, `makePeriodPicker`'s 5th argument, `confirmTap`'s 3rd).
  - Fitting: the toolbar's columns are `minmax(0,1fr)` and `fitLabels()` (called by `fitTools`) shrinks a button's text, 1px at a time down to 10px, until its word fits. `setStatus` re-fits the toolbar when the status line changes height. `tests/i18n.spec.js` checks every language at 1920×950 and that every translation keeps the English placeholders.
  - "File ▸" became **Settings & help ▸** in both apps (`data-act="file"` unchanged).
